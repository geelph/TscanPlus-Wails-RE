# 05 · 指纹库与"配置类"资源解密（AES-128-CBC）

`conf.*` 那一族混淆函数（`UoEhcDLClOvs3` / `Ahm4CSOj8Knikz7` / `GWKfJgPdH0RoV8iN` …）实现的是另一套加解密惯例，管的是"配置类"数据：
内嵌的 **`technologies.json` 指纹库**，以及运行时出现的各种 base64 小串。

工具：[`tools/tscan_cfg_decrypt.py`](../tools/tscan_cfg_decrypt.py)

---

## 1. 三层封装

```
文件 = gzip( base64( AES-128-CBC( json ) ) )
```

导出后直接看文件头就是 base64 文本（`SxHGJM/VBuO3WQrBF+9pb/EyOSVo3Xum…`），比 POC 那边友好得多。

调用链：

```
WProbe.CompileTechnologies
        ↓
conf.UoEhcDLClOvs3(s)     base64.StdEncoding.DecodeString(s) → 取 key → 往下传
        ↓
conf.Ahm4CSOj8Knikz7      aes.NewCipher → cipher.NewCBCDecrypter → PKCS7 去填充
        ↓
conf.GWKfJgPdH0RoV8iN     返回 16 字节 key
```

## 2. key 的来路：常量异或

```
key = "TIDETideTidEtide"        # 16 字节 ASCII
```

`conf.GWKfJgPdH0RoV8iN` 里并没有这个字符串，而是 **4 个 4 字节常量各 XOR 0xD8 后拼起来**（`'T' ^ 0xD8 = 0x8C` 这种形式）。这是最省事的一种"字符串隐藏"，静态看一眼就出来了 —— 和 POC 那边用汇编桩拼口令形成鲜明对比。

两个容易搞错的点：

* **IV 就是 key 本身**，不是密文前 16 字节。工具两种都试（`iv=key` / `iv=head16`），按"解出来像不像 JSON"打分择优 —— 这样换个版本封装变了也不至于直接失败。
* **PKCS7 填充**要手工去（Go 的 `cipher.NewCBCDecrypter` 不自动去填充）。

## 3. 用法

```bash
# 单文件
python tools/tscan_cfg_decrypt.py out/technologies.json -o out/technologies.json.decrypted -v

# 批量（--auto 会递归找 technologies.json 并**原地替换**，密文备份成 *.cipher）
python tools/tscan_cfg_decrypt.py --auto out

# 换 key
python tools/tscan_cfg_decrypt.py in.bin -o out.json --key "xxxxxxxxxxxxxxxx"

# 解那种 base64 小串（无 gzip 层）
python tools/tscan_cfg_decrypt.py --b64 "XDO+lmEHawuskT+iyi2twg=="     # -> 2028.01.01
```

`--auto` 与 `--inplace` 的区别：前者固定原地替换（并留 `.cipher` 备份），后者用于单文件。本仓库采用的是**不改密文、明文另存**（`decrypt_all.py` 的做法），便于与 `manifest.json` 的 sha256 对账。

## 4. 结果

| 项目 | 值 |
|---|---|
| 密文 | `technologies.json` 4,250,752 字节（熵高、base64 文本） |
| 明文 | `technologies.json.decrypted` **3,188,052 字节** |
| 结构 | `{"categories": {...14 类...}, "technologies": [...22003 条...]}` |
| 分类 | CMS / CDN / Device / FrameWork / FrontFrame / Language / Email / OA / Panel / WebService / Widget / FireWall / System / Other |
| 单条字段 | `cats` / `description` / `icon` / `js` / `html` / `headersstr` / `level` …（Wappalyzer 风格） |

```bash
python -c "import json;d=json.load(open('out/technologies.json.decrypted',encoding='utf-8'));\
print(len(d['technologies']),'条指纹 /',len(d['categories']),'分类')"
# => 22003 条指纹 / 14 分类
```

这就是 Finger/指纹识别功能的底库：22003 条规则，覆盖 Web 框架、CMS、中间件、网络设备、安全设备等。

### 同一套算法的另一种用法

`XDO+lmEHawuskT+iyi2twg==` 这类 16/24 字节的 base64 串在程序里到处出现（都是 `conf` 那一族的产物）：

| 明文 | 含义 |
|---|---|
| `2028.01.01` | 授权到期日 |
| 32 字节十六进制串 | 机器码 |
| 短 ASCII | 许可证片段 |

所以 `tscan_cfg_decrypt.py --b64` 可以直接当"配置串解密器"用，不必写新代码。

## 5. `CfgZip.zip`：为什么解不开

`CfgZip.zip`（98 KB，熵 7.99）曾被怀疑是"加密的配置包"，结论是**它不是加密，而是不可用数据**。五条证据：

1. **结构对不上**：长度 100,678 不是 16 的倍数；文件里没有 `PK\x03\x04`、`PK\x05\x06`(EOCD)、gzip、zstd 任何魔数；长度/熵组合符合随机填充。
2. **代码里没有解密步骤**：`core/pkg/file.New` 把它读进全局变量后，`conf.ReadCfgRewriteFromZip(path)` **直接** `archive/zip.OpenReader(path)`，`conf.Unzip.extract` 也是直接 `zip.OpenReader` + `os.MkdirAll`；整条路径没有 `aes` / `gzip` / `base64`。
3. **程序自己也解不开**：删掉 `~/.config/TscanPlus` 触发恢复，日志直接报
   `[WAR] 配置无法恢复，创建默认 config.yaml: 无法加载或恢复 config.yaml`。
4. **穷举过**：用配置密钥（`TIDETideTidEtide`）在 CBC/CTR/CFB/OFB/ECB/GCM 全模式下、0~32 字节各种前缀偏移都试过，全部失败。
5. **商业逻辑解释得通**：Free 版把真正的配置包换成随机填充（占位/诱导），付费版才有内容。

> 结论：不要再在这上面投入。要拿真实内容，只能对比付费版样本（如果它真的存在）。

## 6. 换版本怎么办

| 现象 | 含义 | 处理 |
|---|---|---|
| 解出来不像 JSON（`looks_json: false`） | key 换了 | 重新看 `GWKfJgPdH0RoV8iN`，`--key` 指定 |
| 明文尾部有乱码 / JSON 解析失败 | IV 或填充变了 | `-v` 看层数（`base64 → aes-128-cbc → gunzip` 是否与预期一致） |
| 层数变了（少一层 gzip 等） | 封装调整 | `decrypt_blob()` 会自动剥最多 3 层，多数情况无需改代码 |
